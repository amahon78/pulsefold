# PF-0003: OpenTelemetry Extension Strategy

**Status:** Draft (Grok, 2026-10-12). For Codex review. Decision P-002 remains open; this is a recommendation only.

## 1. Facts about the Collector that drive the decision

- F1. Collector pipelines are receivers → processors → exporters; **connectors** join pipelines and can convert signal types (e.g. `count`, `signal_to_metrics`, `routing`, `failover`) [1][2].
- F2. One receiver can feed **multiple pipelines**; data is fanned out to each. [1]
- F3. Custom distributions are built with the OpenTelemetry Collector Builder (`ocb`) from a manifest listing component Go modules [3]. Upstream ships `otelcol`, `otelcol-contrib`, `otelcol-k8s` distributions [4].
- F4. Exporters use `exporterhelper` with `sending_queue` (in-memory or persistent via a storage extension) and retry; the `memory_limiter` processor refuses data under memory pressure (back-pressure to receivers) [5].
- F5. The relevant primitives already exist in contrib: `logdedup`, `drain`, `filter`, `transform`, `redaction`, `tail_sampling`, `count`, `signal_to_metrics`, `remotetap`, `telemetry_policy` (WIP) (see competitive-landscape.md).
- F6. Contrib releases are frequent (roughly every two weeks historically) and many components are alpha, with breaking config changes called out in changelogs (e.g. drain masking-rules change marked breaking, PR #49954) [6].
- F7. A Go panic in any component crashes the whole Collector process; there is no built-in per-processor "bypass on error" (INFERENCE from Collector architecture; Medium-High confidence — Codex to verify against current `service` code).

## 2. Options

| Criterion | A. Custom Collector distribution (ocb) bundling upstream + PulseFold components | B. PulseFold processors/connectors only (users add to their own Collector) | C. Standalone OTLP proxy (own binary, own pipeline) | D. Hybrid: B as the unit, A as the default packaging, analysis as a separate pipeline/process |
|---|---|---|---|---|
| Exporter ecosystem reuse | Full | Full | **None** (rebuild exporters or chain to a Collector) | Full |
| Contributor ergonomics | Go + Collector conventions (mdatagen, component lifecycle) | Same | Freest | Same as A/B |
| Upgrade burden | High: track contrib cadence, rebuild, CVE patching | Medium: keep compatible with core API versions (`pdata`, component API still pre-1.0 in places) | Low upstream coupling, high self-maintenance | High but shared |
| Performance | Native pdata, no extra hop | Native | Extra hop + serialisation if chained | Native for forwarding path |
| Packaging / first run (PR-014 10-min) | One image, good | Requires users to build/assemble — **fails PR-014** for small teams | One image, good | One image (A) plus "bring your own collector" (B) |
| Config complexity | Collector YAML (familiar to OTel users, intimidating to others) | Same | Can be simple | Ship opinionated presets |
| Failure behaviour / fail-open (PR-006) | Shares process with forwarding: analysis bug can crash forwarding | Same | Can isolate, but proxy itself is a SPOF | **Best**: shadow analysis in a separate pipeline (F2) or separate process fed by a tee, so forwarding path is stock upstream components |
| Duplication risk | Low (reuses contrib) | Lowest | **High** — re-implements Collector | Low |

## 3. Shadow mode mapped onto stock OTel (key finding)

FACT-based construction (F1, F2): shadow mode can be expressed with **no PulseFold code in the forwarding path**:

```yaml
# illustrative only — not product code
service:
  pipelines:
    logs/forward:   { receivers: [otlp], processors: [memory_limiter, batch], exporters: [otlp/backend] }
    logs/analyse:   { receivers: [otlp], processors: [pulsefold_analyser], exporters: [pulsefold_report] }
```

INFERENCE (Medium-High): this satisfies PR-002 (forward unchanged) by construction, and narrows fail-open risk to (a) process crash, (b) memory contention, (c) back-pressure from the analysis pipeline. (c) needs verification: if the analysis pipeline's processor blocks or `memory_limiter` refuses, does the shared receiver return errors to clients for *both* pipelines? Codex must test fan-out back-pressure semantics. Running analysis in a **separate process** fed by an OTLP exporter with a drop-on-full queue removes (a)–(c) at the cost of a hop.

## 4. Recommendation (Confidence: Medium)

**Option D (hybrid)**:
1. The unit of delivery is a small set of Collector components (an analyser processor/connector producing the shadow report; later a compaction-policy processor). Prefer upstream contrib components (`logdedup`, `drain`, `filter`) for actions; contribute upstream where they fall short.
2. Default packaging is an `ocb`-built distribution with opinionated presets (shadow-mode config generated by a `pulsefold init` style flow later).
3. The incident/evidence/routing/investigation control plane is a **separate service** consuming OTLP metrics/logs and report events — not inside the Collector. Keeps the Collector distro small and the slow plane off the hot path (02_ARCHITECTURE §3).
4. Reject Option C for V0: it duplicates the Collector and loses the exporter ecosystem.

Assumptions: users accept Collector YAML; Go remains the core language (P-001). Contrary evidence: Sawmills/Edge Delta show customers like a UI over YAML; Collector config is a known adoption barrier.

## 5. Things Codex should verify (not verified here)

- Fan-out back-pressure semantics when one pipeline refuses (F2/§3).
- Whether processor panics are recovered anywhere in current Collector (F7).
- Component API stability levels (`pdata` is 1.x; component/processor helper APIs status).
- Persistent queue durability guarantees for evidence/archive exporters.
