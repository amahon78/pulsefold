# PF-0006: OpenTelemetry implementation verification

**Reviewer:** Codex
**Date:** 2026-10-12
**Scope:** Verification of the Collector claims in the Phase 0 research against upstream source, not a product implementation or a benchmark result.

## Findings

| ID | Finding and evidence | Status | Risk | Recommendation |
|---|---|---|---|---|
| OTV-01 | A receiver configured in more than one pipeline is constructed with `fanoutconsumer.New*`; pipeline receivers are called synchronously. The fan-out implementation invokes each consumer in sequence and returns a combined error. See [receiver construction](https://github.com/open-telemetry/opentelemetry-collector/blob/e85aabce57ebef50de20837dca46fb6f4a483f04/service/internal/graph/receiver.go) and [log fan-out](https://github.com/open-telemetry/opentelemetry-collector/blob/e85aabce57ebef50de20837dca46fb6f4a483f04/internal/fanoutconsumer/logs.go). | **Verified.** Grok F2 is true, but the proposed two-pipeline shadow diagram implies isolation that is absent. | A slow, blocked or erroring analysis branch delays the shared receiver and returns an error alongside the forwarding result. Mutating branches also cause full pdata clones. | **Reject** shared-receiver fan-out as the V0 availability boundary. Treat it as a functional duplication mechanism only. Test every proposed topology under a blocked analyser. |
| OTV-02 | `memory_limiter` returns a non-permanent error to its caller once its soft limit is exceeded. Its documentation states that a preceding component which does not retry loses data. | **Verified.** [Memory limiter README](https://github.com/open-telemetry/opentelemetry-collector/blob/e85aabce57ebef50de20837dca46fb6f4a483f04/processor/memorylimiterprocessor/README.md). | A memory-limited analysis branch on a shared fan-out can propagate backpressure to production senders. It is not a harmless local shedder. | **Accept** memory limiting, but only as an explicit availability policy. Put a limiter first in each telemetry pipeline and measure receiver retry behaviour. Do not call this fail-open. |
| OTV-03 | `exporterhelper` provides retry and bounded in-memory or persistent queues. Queue admission failure is normally a drop, is observable via enqueue-failed metrics and does not enter retry logic. Persistent queues resume queued batches after restart, subject to their storage extension working. | **Verified.** [Exporter helper README](https://github.com/open-telemetry/opentelemetry-collector/blob/e85aabce57ebef50de20837dca46fb6f4a483f04/exporter/exporterhelper/README.md). | A queue is neither a lossless guarantee nor a process-isolation mechanism. With several consumers it also does not promise delivery order. Disk-full and permanent errors remain loss paths. | **Accept with limits.** Report queue capacity, admission failures, retry exhaustion, storage failures and recovery behaviour. Do not describe persistent queues as evidence durability without an end-to-end crash test. |
| OTV-04 | A component panic is an ordinary Go panic unless its own code recovers it. The inspected service lifecycle starts and stops components but contains no generic `recover` around component calls. | **Verified with bounded scope.** [Service lifecycle](https://github.com/open-telemetry/opentelemetry-collector/blob/e85aabce57ebef50de20837dca46fb6f4a483f04/service/service.go), [consumer interface](https://github.com/open-telemetry/opentelemetry-collector/blob/e85aabce57ebef50de20837dca46fb6f4a483f04/consumer/consumer.go). Kubernetes restart only converts this to an interruption, not transparent forwarding. | **Accept** separate OS processes for production forwarding and non-essential analysis. Add panic and restart tests before claiming failure safety. |
| OTV-05 | `log_dedup` accumulates eligible records for an interval, removes them from the incoming batch and emits aggregates asynchronously. Its code sets `Timestamp` to emission time and `ObservedTimestamp` to the first processor-observed time, while first and last observed times are also attributes. This conflicts with its README statement that both timestamps are emission time. It logs downstream consume errors during flush then resets the aggregate. | **Verified source discrepancy.** [Processor](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/7be474ae4e2a7612b126ecb1435c36de64b00d87/processor/logdedupprocessor/processor.go), [counter/export behaviour](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/7be474ae4e2a7612b126ecb1435c36de64b00d87/processor/logdedupprocessor/counter.go), [component README](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/7be474ae4e2a7612b126ecb1435c36de64b00d87/processor/logdedupprocessor/README.md). | It changes log time semantics and can lose an aggregate when the downstream consumer fails at flush. It is not an evidence-preserving or pass-through primitive. | **Accept as a benchmark baseline only. Reject** using it in shadow forwarding or active compaction until semantics, recovery and downstream-query effects are independently tested. |
| OTV-06 | Exact identity in `log_dedup` is not full-byte equality. It uses a 64-bit pdata hash of body, attributes and severity, then uses that hash directly as the map key. Resource and scope are separately 64-bit hashed. With `include_fields`, only selected field values are hashed. | **Verified and materially disputed.** [Key construction](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/7be474ae4e2a7612b126ecb1435c36de64b00d87/processor/logdedupprocessor/counter.go). | Hash collisions and selected-field collisions can merge distinct records. The upstream component is suitable for configurable aggregation, but does not meet PulseFold's proposed no-lossy-hash safety invariant. | **Reject** the claim that C1 can be reused unchanged for a safety-critical guarantee. For any PulseFold active policy, use canonical identity plus full equality verification, or explicitly state the residual collision risk. |
| OTV-07 | `log_dedup` has a global processor mutex for intake, keeps all unique records across the interval in memory, and has no overall unique-log cardinality cap. `metadata_cardinality_limit` only bounds client-metadata shards and defaults to unlimited. | **Verified.** [Processor state and locking](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/7be474ae4e2a7612b126ecb1435c36de64b00d87/processor/logdedupprocessor/processor.go), [configuration](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/7be474ae4e2a7612b126ecb1435c36de64b00d87/processor/logdedupprocessor/config.go). | High-cardinality or large-body traffic can create memory pressure and serialise ingestion. Metadata partitions can additionally multiply state. | **Reject** it as an unqualified scalable C1 implementation. Benchmark it with adversarial unique records, large bodies and metadata partitions. Any future PulseFold state must have byte, entry and time caps with a pass-through overflow policy. |
| OTV-08 | `drain` annotates log records only. It serialises calls to `Drain.Train` with a mutex, holds an in-memory parse tree, and defaults `max_clusters` to zero, meaning unlimited. It can persist a full snapshot through a storage extension. | **Verified.** [Processor](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/7be474ae4e2a7612b126ecb1435c36de64b00d87/processor/drainprocessor/processor.go), [configuration](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/7be474ae4e2a7612b126ecb1435c36de64b00d87/processor/drainprocessor/config.go), [persistence](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/7be474ae4e2a7612b126ecb1435c36de64b00d87/processor/drainprocessor/storage.go). | At V0 defaults it permits unbounded clusters and serialises template learning. | OTV-09 | Drain's template is state-dependent. Arrival-order dependence is a reasonable algorithmic inference because records train a mutable tree, but upstream does not state it as a formal guarantee. Its documentation says that instances build independently and only describes convergence given representative forms. Snapshot writes use a single fixed key, have no compare-and-swap or merge, and the documentation labels multi-instance tree merging a future extension. | **Verified facts plus stated inference.** [Deployment discussion and future work](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/7be474ae4e2a7612b126ecb1435c36de64b00d87/processor/drainprocessor/README.md), [storage implementation](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/7be474ae4e2a7612b126ecb1435c36de64b00d87/processor/drainprocessor/storage.go). | Grok's stronger claim of permanent divergence remains an inference, not a verified fact. Conversely, identical cross-instance template IDs are not guaranteed. Concurrent writers can overwrite a useful snapshot with another valid but different tree. | **Investigate.** Benchmark shuffled, partitioned streams across 2–4 instances and fail the candidate for unsafe merge rate or unacceptable template disagreement. Do not use a template string as a globally stable evidence identity. |
| OTV-10 | Drain masking rules replace matching body text before training, but can emit raw matched parameters and wildcards as log attributes. The component does not provide a general secret/PII redaction boundary. The contrib redaction processor is one defence and must be ordered before any component that stores or derives from sensitive input. | **Verified.** [Drain parameter extraction](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/7be474ae4e2a7612b126ecb1435c36de64b00d87/processor/drainprocessor/processor.go), [redaction README](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/7be474ae4e2a7612b126ecb1435c36de64b00d87/processor/redactionprocessor/README.md). | A secret can otherwise reach a template, hash, snapshot or evidence record. Enabling `emit_wildcards` or named parameters reintroduces raw sensitive values. | **Accept decision E.** Redact before fingerprinting, template training, persistence and any model boundary. Disable raw parameter extraction by default. |
| OTV-11 | The Collector Builder can produce custom distributions from a component manifest. ## Fan-out, backpressure and isolation conclusion

The following distinction must be explicit in architecture and user documentation:

```text
One receiver, two Collector pipelines
  = synchronous functional fan-out, shared process, shared memory and shared fate

Separate forwarding and analysis processes
  = process isolation only if the replication boundary has a bounded, explicitly
    lossy or durable delivery contract independent of the forwarding call path
```

No in-process topology can guarantee the PR-006 meaning of fail-open against panic, memory exhaustion or a synchronously propagated downstream error. A production claim requires an end-to-end experiment using the exact receiver, exporter, queue and upstream SDK retry configuration.

## Required experiments before an implementation decision

1. Block the analyser exporter, fill its queue and measure forwarding latency, receiver responses and dropped counts for a shared receiver fan-out.
2. Crash the analyser process, crash a processor and exhaust disk backing a persistent queue. Verify downstream delivery, duplicates and recovery.
3. Drive C1 with unique 1 KiB and 1 MiB logs at the target rate. Record heap, GC, mutex contention, queue depth and refusal behaviour.
4. Run Drain across independently shuffled streams on multiple instances. Measure template agreement, unsafe merges, cold-start behaviour and state overwrite behaviour.
5. Put a fake secret in body, attributes and a structured body. Confirm that neither fingerprints, templates, snapshots, reports nor model payloads contain it after redaction.

## Decision

**Recommendation: accept the hybrid direction, but reject its current shared-pipeline shadow-mode example as a safety design.** Reuse upstream components as baselines and optional integration points, not as proof that PulseFold's safety, evidence or availability guarantees already exist.
